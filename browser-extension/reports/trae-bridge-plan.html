browse 连接层重做：Trae-style Browser Bridge

结论：撤回 CDP 方案；按本机 Trae CN 的真实实现，把 daemon + native host + wrapper 三层换成一个独立的 browser-bridge 常驻服务，扩展直连。

证据类型：类1 官方 类3 本机二进制 strings 推测 ｜ 2026-09-15

一、Trae Worker 到底怎么做的（实证）

本机 /Applications/Trae CN.app/Contents/Resources/app/modules/browser-bridge/browser-bridge 是 Rust 编译的独立常驻服务（Mach-O arm64，源码路径字符串 apps/icube_server_rs/modules/browser-bridge/src/main.rs）。类3 · strings 实证

通道：UDS + trae-browser-bridge.sock（Unix 套接字，本机进程间管道）；同时含 TCP + 127.0.0.1:19234（只监听本机的 TCP 口）
认证：_auth 字段族 —— nonce（一次性随机数）、timestamp、signature、HMAC signature mismatch（HMAC 签名校验失败的原话）、browser-bridge-xor-mask-key!!@@#（混淆 key 常量）、Received request before auth, closing connection（没认证先发请求 = 直接断）、Auth timeout (5s)
保活：heartbeat、Chrome channel closed、Client disconnected
请求模型：method / id 字段对 —— 每条请求带方法名和唯一 id

密钥怎么生成、握手字段顺序 —— 仅 strings 看不出，需要: 反汇编或抓包确认，不猜。

浏览器扩展
    │  本机 TCP 127.0.0.1:19234 或 Unix socket
    ▼
browser-bridge（Rust 常驻服务，唯一连接中心）

Trae 主程序 / Worker

Trae 的要害不是「用哪种 socket」，而是：bridge 是唯一连接真相。没有 per-browser manifest、没有 wrapper 猜身份、没有第二层中转。

二、现在的 browse 为什么不稳（已发生的实锤）

事故根因（file:line）
没装 opera，status 却显示「opera 已连接」lib/browse_install.py 旧 BROWSERS 表：brave/opera 写进 Chrome 共享 manifest 目录，后写的 wrapper 覆盖先写的，Chrome 的扩展 fork 到 opera 的 wrapper
Chrome / Arc 互踢闪断（一半 E2E 指令 rc=3）Arc 读 Chrome 目录（类3 Reddit/StopTheMadness），与 Chrome 同槽；24 秒采样抓到两个 native host 分别父进程为 Chrome 和 Arc
daemon 停后扩展不回连MV3 service worker 空闲 30 秒被杀，重连定时器随它死（已用 alarms 缓解，治标）
wrapper 判身份失败Chrome fork 出的子进程 $PPID 不是浏览器主进程，case 匹配落空

这三层里每一层都有自己的生命周期，各自断线、各自重连、状态互不同步 —— 结构性不稳，不是 bug。

三、新架构：browse browser-bridge

browse CLI ─┐
            ├─ Unix socket ─▶ browser-bridge（常驻，唯一连接中心）
Arc 扩展 ───┤                    │  连接表 / heartbeat / HMAC 认证
Chrome 扩展 ┘                    ▼
                          dispatch()（现有 handler 全保留）
逐条对应 Trae 的做法：
能力实现
扩展直连SW 启动即连 ws://127.0.0.1:9229（WebSocket；Chrome 116+ 收发消息自动给 SW 续命，类1 developer.chrome.com/docs/extensions/how-to/web-platform/websockets）
认证首条消息 _auth{nonce,timestamp,signature}，HMAC；未认证先发请求 = 断开（对齐 Trae 的 Received request before auth, closing connection）
保活heartbeat 每 10–20 秒（官方示例用 10s，类2 GoogleChrome/chrome-extensions-samples tutorial.websockets）
多浏览器按 connectionId 隔离；browserName 只是展示字段 —— Chrome/Arc 共用扩展包也不再互踢
状态真相bridge 持有连接表：谁连着、上次心跳几秒前、重连过几次、上次断线原因；browse status 直接读它，不再从 manifest 反推
安装不再写任何 native-messaging manifest / wrapper / 注册表；装完扩展自动连，无需重启浏览器

为什么选 WebSocket 而不是让扩展连 Unix socket：浏览器沙箱里扩展代码只能开 TCP/WebSocket，够不到 Unix 套接字；CLI 侧才用 Unix socket 连 bridge。推测: 端口 9229 是占位，实现时定

四、为什么落选另外两条

落选方案什么条件下才对
CDP（--remote-debugging-port）Chrome 136 起对默认用户数据目录禁用（类1 developer.chrome.com/blog/remote-debugging-port）——你的日常浏览器带全部登录态，按定义就在默认目录，此路不通。只在「愿意用一个独立的自动化专用浏览器实例」时才对
继续修 native messaging只在「必须让扩展从浏览器拿到第一推动力（浏览器主动 fork 本地程序）」时才对——那正是 Trae 没选的路
